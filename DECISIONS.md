## followup-7: The 4 MB output budget is a hard bound on the in-memory capture
- **What:** n2's stated trade-off — "output retained for parsing is capped at 4 MB in memory; `command.log` on disk is never truncated" — now holds under measurement rather than by intent. ## followup-11: A slow disk degrades the log, never the verdict
- **What:** The headless lane no longer lets `command.log` apply backpressure to the command it is logging. `src/lanes/headless/runner.ts` routes all log output through a new exported `LogSink` class: `write()` is non-blocking by construction, the stream's queue is capped at `MAX_BUFFERED_LOG_BYTES` (8MB), and output arriving while the queue is over that cap is dropped **from the log only** — never from the in-memory `CappedText` the status and `failures[]` are computed from. When the sink catches up, a `[offstage] ---- N bytes omitted here: the disk could not keep up ---- ` marker is written at the point of the hole. After the command exits, `LogSink.close()` waits for the queue to drain but stops at the caller's deadline (`timeoutMs + LOG_FLUSH_GRACE_MS`, 2s) or once the queue has not shrunk for `LOG_FLUSH_STALL_MS` (5s), whichever comes first. Any shortfall is stated in `diagnostics` alongside an explicit sentence that the verdict was not affected.
- **Why:** Verified empirically on darwin/arm64 against a real FIFO sink, not reasoned about. A fixture printing 4MB that exits 0 in 68ms on a fast disk was, on the pre-fix code: (a) with backpressure honoured (`await` the write, the shape followup-7 was landing), blocked on a full pipe and killed by its own 20s timeout — reported `status: 'errored'` with "the command never finished, so nothing can be concluded about the code under test", which was false, the disk was slow and the code was fine; (b) with backpressure ignored (`write()` and drop the `false`, the shape on main), queued ~4MB in memory unbounded — defeating the very cap `MAX_CAPTURED_CHARS` exists to enforce — and returned after 24,595ms against a 20,000ms deadline; and (c) against a fully wedged sink, **never returned from `run()` at all** (killed by a watchdog at 40s). For a product whose entire thesis is an honest verdict, a lane that blames the code under test for the disk is the worst available failure, so the log is the thing that gives way.
- **Marker semantics, for anyone reusing `LogSink`:** the omission marker is written when the sink recovers mid-run, and — if it never recovers — once more at `close()`, so a log that was cut short still testifies to its own gap. ## followup-11: `timeoutMs` bounds the command, plus a small stated logging grace
- **What:** `timeoutMs` continues to bound the command itself (execa kills the child). On top of it, `run()` may spend up to `LOG_FLUSH_GRACE_MS` (2s) flushing the log after the command has already finished, and no more — so the wall-clock ceiling for `run()` is `timeoutMs + 2s`. When the caller passes no `timeoutMs`, the flush is bounded instead by `LOG_FLUSH_STALL_MS` (5s) of *no progress*: a sink that is still draining, however slowly, is allowed to finish, because truncating a log that is actively being written would be gratuitous.
- **Why:** Before this, `timeoutMs` bounded nothing after the child exited — execa's timer is cleared when the subprocess settles, so the post-exit flush ran unbounded and was measured overrunning a 20s deadline by 4.6s, and hanging indefinitely on a wedged sink. A caller that asks for an answer within a deadline should get one. Distinguishing "slow but draining" from "wedged" by watching the queue actually shrink is what lets the common case (a big log on a slowish disk) complete intact while the pathological case is still bounded.
- **Consequences for siblings:** n6/n7/n9 can rely on `headlessLane.run()` returning within `timeoutMs + 2s` and should size their own outer timeouts above that rather than equal to `timeoutMs`. The poll timer inside `LogSink.close()` is deliberately **not** `unref`'d: an unref'd timer would let a process whose only remaining work is the flush exit out from under it, losing the log and never resolving `run()`.

## n9: End-to-end integration, and the difference between green and verified

- **Did:** Added `tests/e2e.test.ts` (6 tests) which fakes nothing: it stages a real fixture repository, drives the real `offstage` command tree against it, and reads the `result.json` that lands on disk. It holds that `route` and `run` agree, that the persisted envelope re-validates and equals what the CLI printed, that a red suite is `failed` (with parsed failures) rather than `errored`, that two concurrent runs get distinct directories, and that `--lane headless -- xcodebuild test` executes nothing. It also spawns the built `dist/cli/index.js` as a real process, which is what makes the `bin` declarations checkable end to end. When a run does not come back with the expected status, the assertion message carries the run's own `diagnostics` and the tail of its `command.log` — an end-to-end failure that reports only "expected 1 to be 0" hides the one piece of evidence that explains it, in a directory the test then deletes. Ran the clean-clone gate for real — `rsync` of the tree without `node_modules`/`dist`, then `npm ci && npm run build && npm test`: 26 files, 769 passed, 2 expected fail, 7 skipped, exit 0. Wrote `docs/verified.md` recording, per lane, what was exercised live versus in degraded mode, on a named machine, with verbatim `offstage doctor` output.
- **Why the e2e fixtures stage outside the repository, with a symlinked `node_modules`:** Two constraints pull against each other. The fixtures import `vitest/config`, which node resolves by walking parents to a `node_modules` — under `os.tmpdir()` there is nothing to walk up to, and the fixture fails to load its own config before offstage is involved at all. Staging inside the repository fixes that for free, and was the first implementation. It was **wrong, and flaky**: roughly one full-suite run in three, the staged copy was gone by the time the inner vitest read its own `vitest.config.mjs` (`Cannot resolve entry module`) or its test file (`Cannot find module`), because the outer vitest run owns that tree. The fix is to stage in `os.tmpdir()` and symlink the repository's `node_modules` into the copy, excluding the fixture's own `node_modules` (a stale vitest result cache) so the symlink can be created and no run inherits another's cache. Confirmed with 8 consecutive clean full-suite runs after a failure rate of about 1 in 3 before. The lesson worth keeping: a test that writes into the tree its own runner owns will race with it eventually, and the failure will look like a product bug.
- **Follow-ups:**
  - The 7 skipped tests are gated on absent substrates, and each names its gate [accepted] — 5 need `@playwright/test` plus a cached Chromium, 2 need a running container runtime. Playwright is deliberately not a devDependency: a ~150MB browser download on every clean install of a project whose own tests do not need a browser is a poor trade. `docs/verified.md` has the table and the commands that turn each row green.
  - n0's note about `npm ci` leaving esbuild/fsevents scripts unapproved [confirmed harmless] — the clean-clone gate reproduced the warning and passed regardless, on npm 11.19.0.

## n10: Review pass — two real holes in the routing thesis, both closed

- **Did:** Read the assembled tree adversarially and fixed what was actually wrong. Full findings, severities and accepted risks are in [docs/review.md](docs/review.md). Two were genuine safety defects: `env PWDEBUG=1 npx playwright test` routed to `headless` at **high** confidence (the assignment is peeled off as a transparent prefix, so every downstream rule saw a plain Playwright run), and `sh -c 'npx playwright test --headed'` hid the deciding flag inside a single argv token. Both would have put a real window on the real screen. Fixed in the router (`envPrefixSignals`, and `shellDashC` unwrapping in `buildViews`) and again one layer down in `detectHeadedRequest`, so the headless lane refuses such a request rather than trusting its caller. `tests/router.adversarial.test.ts` (26 tests) holds both, plus the cases the node prompt named: a project-level `headless: false` override, `--headed` after a `--`, `xcodebuild` wrapped in `npm run`, a puppeteer script computing headless at runtime, and a repository containing both an `.xcodeproj` and a Playwright config. Corrected README's status table, which listed every implemented module as "in progress" and claimed nothing had been verified live while the headless lane had been.
- **Why the two new readers do not break the no-execution rule:** Both parse text. `shellDashC` tokenizes a `-c` string exactly as the router already tokenizes a `package.json` script, and `envPrefixSignals` reads assignments that `normalizeInvocation` had already collected into `invocation.prefixes`. `tests/router.purity.test.ts` still passes unchanged.
- **Consequences for siblings:** `SignalKind` gains `'headed-env'` and `'headless-env'` — exhaustive switches over it need the arms. `sh`/`bash`/`zsh`/`dash`/`ksh`/`fish` with `-c` now produce a nested `CommandView` labelled `<shell> -c`, so `RouteDecision.signals` can name that origin.
- **Accepted, not fixed:** an exported `HEADLESS=false` in the user's shell is not treated as a headed signal (written into the command it is; the asymmetry and its reasoning are in docs/review.md); a run produces no live output because `LaneRunner` has no streaming hook; a `SIGKILL` of the offstage process can leak a container; the vm lane has still never driven a real macOS guest.
